# Callbacks

UniPAY tells your server about an order's outcome by calling your callback URL. This is the
**only reliable signal** that an order was paid. Redirects back to your site are not.

## Where they go

- Alias `custom`: the base64 `CallBackUrl` you sent when creating the order.
- Alias `api`: the project's callback URL from the business portal.
- Recurring subscription charges: the plan's `callback_url`
  (see [saved-cards-and-subscriptions.md](saved-cards-and-subscriptions.md)).

## The request

```http
POST https://shop.example/webhooks/unipay?MerchantOrderID=ORD-1001-a1&Status=3&Hash=95d6…9039&Amount=25.00&UnipayOrderID=MP5005000012343A1B2C3D4E5F6&ErrorCode=0&ErrorMessage=OK&Reason=&Version=2
Content-Type: application/json

[]
```

- **Every field is in the query string**, form-encoded (a space arrives as `+`). The body is
  always the two characters `[]`, so ignore it.
- Fields whose value is null are left out, and empty values arrive as `Key=`.
- Any 2xx response counts as delivered, and the body you return is ignored. Anything else
  (or a timeout) is retried: **3 attempts in total, about 10 seconds apart**. After that UniPAY
  stops trying.
- The first attempt is made while UniPAY is still finishing the payment, so respond fast
  (well under 30 seconds): verify, record, answer 200, and do slow work afterwards.

## Fields

| Field | Present | Value |
|---|---|---|
| `MerchantOrderID` | always | your reference from `order/create`. For refunds, the original order's. For recurring subscription charges, a UUID generated by UniPAY. |
| `Status` | always | numeric status, see the table below |
| `Hash` | always | signature, see "Verifying" |
| `Amount` | always | decimal with 2 places, e.g. `25.00` (see the notes per status) |
| `UnipayOrderID` | always | the order **hash** (`MP…`), i.e. `UnipayOrderHashID` from `order/create`, **not** its numeric `UnipayOrderID` |
| `ErrorCode` | usually | `0` on success; the bank's code on failure; empty for refunds |
| `ErrorMessage` | usually | `OK` on success; the failure reason otherwise |
| `Reason` | usually | empty on success; the failure reason otherwise |
| `Version` | always | `2` |
| `CardNumber` | card saving and subscriptions only | base64 of the masked card, e.g. `NCAqKiogMTExMQ==` = `4 *** 1111` |
| `RegularPaymentID` | card saving and subscriptions only | saved card token `card_…` |
| `SubscriptionContractID` | subscriptions only | contract UUID |
| `SubscriptionContractStatus` | subscriptions only | `active`, `inactive` or `suspended` |

## Statuses you will receive

| `Status` | Meaning | `Amount` |
|---|---|---|
| `3` | **Paid.** Also sent after a preauth capture and for each successful saved-card or subscription charge. | amount charged (for a preauth capture: the captured amount) |
| `13` | Failed or declined by the bank (also a failed preauth capture) | order amount |
| `22` | The payer reached the bank page but the payment timed out | order amount |
| `-1` | Cancelled by the payer on the payment page, or rejected when starting the payment | order amount |
| `5` | A refund of this order settled, **partial or full** | refund amount **plus the refund fee** |
| `4` | A reversal (same-day cancellation) of this order settled, partial or full | reversed amount |

No callback is sent for:

- orders that are abandoned or expire unpaid (they become 23 INCOMPLETE silently);
- a preauthorization that is approved and put on hold (status 2), until you capture it;
- subscription cancel and update calls;
- anything done with sandbox credentials;
- any order whose `MerchantOrderID` was already used by another order that succeeded.

Reconcile those with `GET /v3/{alias}/order/get-details/{hash}`
(see [statuses-and-errors.md](statuses-and-errors.md)).

## Verifying

```
expected = lowercase_hex( sha256( UnipayOrderID + "|" + MerchantOrderID + "|" + Status + "|" + SECRET ) )
valid    = constant_time_equals(expected, Hash)
```

- `SECRET` is the project's **production** secret key, the same key used for `/v3/auth` with
  the production merchant ID.
- Use the raw decoded query values exactly as received (`Status` such as `3` or `-1`).
- Only `UnipayOrderID`, `MerchantOrderID` and `Status` are signed. `Amount`, the card fields
  and the error fields are not, so before fulfilling an order **compare `Amount` with the
  amount you stored**. If they differ, don't fulfil, and check with `get-details`.
- There's no timestamp, so a valid callback could be replayed. Idempotent processing makes that
  harmless.

Test vector: secret `test_secret_123`, `UnipayOrderID=MP1234567A1B2C3D4E5F6`,
`MerchantOrderID=ORDER-1001`, `Status=3` gives
`95d6a872e92c3b6cb19e6e422a3ad8c78f5f8bc491ef4e491155c1bb57289039`.

The examples folder has ready-made verifiers in PHP, Node and Python.

## Processing correctly

1. Read the parameters from the query string and verify `Hash`. Reject a bad hash with 400.
2. Find your order by `UnipayOrderID` (the hash you stored at creation); `MerchantOrderID` is
   a fallback.
3. Apply the status **idempotently**: one order can receive several callbacks (payment, then
   refunds) and each may be retried. Keying on (`UnipayOrderID`, `Status`, `Amount`) is
   enough to ignore duplicates. Never move an order from paid back to pending.
4. For `Status=3`, check `Amount` equals what you expect, then mark the order paid.
5. Answer 200.

## Subscription-expired notice

When a suspended subscription finally lapses, UniPAY sends a different, signed webhook to the
plan's `callback_url`: a JSON body (also copied into the query string) with `CardNumber`,
`RegularPaymentID`, `SubscriptionContractID` and `SubscriptionContractStatus: "inactive"`,
and a header `Signature: hex(HMAC-SHA256(key = production secret key, message = raw body bytes))`.
Verify the HMAC over the **raw** body as received; don't re-serialize the JSON. Up to 3
attempts, with a 3-second timeout.
